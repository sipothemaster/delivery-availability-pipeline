# Data Model

This document describes data the software can create in a private deployment.
No records from these tables are distributed with the repository.

## Analytical Entities

### Static Coverage

Grain: one recorded `postcode` and `restaurant_id` pairing for a source
snapshot.

Typical fields:

- `snapshot_label`
- `postcode`
- `restaurant_id`
- `is_delivery`
- `delivery_fee`
- `minimum_delivery_value`
- `delivery_eta_lower_minutes`
- `delivery_eta_upper_minutes`
- `drive_distance_meters`

This table is reconstructed from private raw listing responses. `is_delivery`
describes the source response state and must not be interpreted as proof that a
restaurant always or never delivers to the postcode.

### Restaurant Profile

Grain: one row per `restaurant_id`.

Typical fields:

- restaurant name and platform identifier;
- stable platform slug and restaurant URL;
- address, city, postal code, latitude, and longitude where supplied;
- cuisine identifiers and names; and
- rating and review count where supplied.

The profile table contains reusable identity attributes. Opening intervals,
postcode-specific delivery state, and observations over time belong in separate
tables.

### Opening Schedule

Grain: one `restaurant_id`, `service_type`, `day_of_week`, and opening interval.

Core fields:

- `opening_time_id`
- `restaurant_id`
- `restaurant_unique_name`
- `service_type`
- `day_of_week`
- `interval_index`
- `opens_at_local`
- `closes_at_local`
- `crosses_midnight`
- `timezone`
- `source`
- `fetched_at`

A restaurant with two service periods on the same day produces two rows. An
overnight interval remains attached to its source day and is marked with
`crosses_midnight`; it is not silently split or moved to another weekday.

### Observed Availability

Grain: one `postcode`, `planned_window`, and restaurant observation generated by
a successful job.

Core provenance fields include `snapshot_id`, `job_id`, `provider`, `postcode`,
`planned_window`, `scheduled_at`, and `captured_at`. Listing fields include
restaurant identity, rating, categories, delivery time, fee, minimum order,
offers, tags, URL, and cuisine identifiers when available.

The production parser includes a restaurant only when the source record reports:

```text
isDelivery = true
isOpenNowForDelivery = true
isTemporarilyOffline = false
```

This table is therefore an observed open-now table, not the complete universe of
postcode-to-restaurant relationships.

## Operational Provenance

The pipeline uses separate operational tables for:

- deterministic task manifests;
- append-only job events;
- request and limiter diagnostics;
- worker job state;
- menu-manifest task state; and
- menu-manifest fetch outcomes.

These tables provide execution evidence but are not substitutes for analytical
tables. Event and diagnostic records should be used to assess completion when a
mutable manifest status is incomplete.

## Relationships

```text
restaurant_profile.restaurant_id
  -> static_coverage.restaurant_id
  -> observed_availability.restaurant_id
  -> restaurant_opening_times.restaurant_id

job_manifest.job_id
  -> job_events.job_id
  -> job_diagnostics.job_id
  -> observed_availability.job_id
```

Joins must respect table grain. Joining a restaurant profile to postcode
coverage is one-to-many; joining opening intervals can multiply each restaurant
by service, weekday, and interval.

## Time Semantics

- `scheduled_at` is the intended Cloud Tasks execution time.
- `captured_at` is when a worker captured the upstream response.
- `planned_window` labels the research observation window.
- Opening times are local wall-clock strings accompanied by a timezone.
- Collection windows should be stored and interpreted in `Europe/London` when
  reproducing the original UK research design.

## Missingness And Quality

- No listing rows for a postcode does not establish that no service exists.
- Missing opening intervals do not imply `is_delivery=false`.
- Temporary offline state should not be collapsed into permanent absence.
- ETA and fee values are observations and may include source outliers.
- Historical postcodes and geography joins require a separate quality audit.
- Provider fields and undocumented semantics can change over time.
